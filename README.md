# Автоматическая установка IPv6-прокси

Установщик создаёт **заданное число логических прокси на новом сервере**. Нужны
SSH-хост, пользователь, пароль или ключ и количество прокси. IPv4, интерфейс и
IPv6-подсеть определяются по настройкам сервера, если выбор однозначен.

## Архитектура

Один процесс 3proxy 0.9.5 обслуживает один входящий IPv4-порт. У каждого прокси
свой логин и пароль, а правило `parent ... extip` закрепляет за логином конкретный
исходящий IPv6. Адрес не меняется между запросами и переподключениями.

Формат списка сохранён:

```text
192.0.2.10:10000@capacity_00001:password_1
192.0.2.10:10000@capacity_00002:password_2
```

Для `/48` каждый прокси получает адрес из отдельной `/64`; для `/64` все адреса
остаются в одной подсети. Это не создаёт разные `/48`, ASN или независимую репутацию
адресов. Установка не изменяет выделение подсетей у провайдера.

Количество логических прокси, число одновременно открытых соединений и HTTP RPS —
разные величины. Большой пул адресов может обслуживаться одним слушателем, однако
активные HTTP-соединения и WS продолжают расходовать память и CPU.

Обоснование выбора и измеренные профили: [архитектура и испытания](docs/architecture.md).

## Запуск с локальной машины

Поддерживаются Ubuntu/Debian с systemd и root-доступом. Основная IPv6-сеть и маршрут
должны быть настроены провайдером. Сначала проверьте обычное SSH-подключение:
установщик использует `~/.ssh/config`, ключи/agent и известные ключи из `known_hosts`.

```bash
python3 -m venv venv
venv/bin/pip install -r requirements.txt
venv/bin/python remote_setup_script.py --host 192.0.2.10 --target-count 3000
```

Дополнительные параметры:

```bash
# Другой ключ или пользователь
venv/bin/python remote_setup_script.py --host proxy-host --user root \
  --key ~/.ssh/proxy_key --target-count 9000

# Пароль SSH вводится скрыто, в аргументы процесса не попадает
venv/bin/python remote_setup_script.py --host 192.0.2.10 --password --target-count 3000

# Явные сетевые параметры при неоднозначной конфигурации
venv/bin/python remote_setup_script.py --host 192.0.2.10 --target-count 3000 \
  --interface net0 --external-ipv4 192.0.2.10 --ipv6-subnet 2001:db8:1234::/48
```

`--project-prefix` задаёт имя единственного проекта, по умолчанию `capacity`.
Размер пачки не задаётся. `--target-count` означает количество при первой установке;
повторный запуск для увеличения или уменьшения пула запрещён.

### Этапы установки

1. Получить код через Git и проверить отсутствие существующего либо незавершённого пула.
2. Определить сеть; при неоднозначности остановиться с названием нужного параметра.
   Например, наличие `/64` не считается доказательством выделенной провайдером `/48`.
3. Установить зависимости и закреплённую версию 3proxy.
4. Атомарно сформировать полный набор адресов, учётных данных и конфигурацию.
5. Пакетно привязать IPv6, дождаться завершения DAD, включить службу systemd.
6. Проверить слушатель, службу и запас доступной памяти не менее 512 МиБ.
7. Скачать списки и с локальной машины проверить **каждый** прокси: входящий порт
   доступен извне, HTTPS проходит, наблюдаемый IPv6 совпадает с назначенным.
8. Объявить завершение только после успешной проверки полного количества.

Служба получает ограничение памяти, рассчитанное из доступной памяти перед запуском
с резервом 512 МиБ. Это защита ресурсов сервера; допустимая рабочая нагрузка задаётся
отдельным измеренным профилем. Технический `maxconn` не является гарантией ёмкости.

### Результат и ошибки

Локально в `downloaded_configs/<host>/` сохраняются:

- `extracted_proxy` — общий список;
- `deployment.json` — состояние, количество, сеть, версия кода и бюджет памяти;
- `<project>/proxy_configs` — соответствие логинов и IPv6;
- `<project>/pool.json` — тип идентичности и параметры пула;
- `<project>/proxy_check_results.txt` — результаты внешней проверки без паролей.

Каталоги приватные, файлы с доступом — 0600. Списки скачиваются и при ошибке создания;
ошибка проверки сохраняется вместе с результатами, не скрывается частичным успехом.

Состояния: `creating`, `started_unverified`, `complete`, `failed`,
`verification_failed`. Только `complete` означает завершённую установку.
`--skip-check` оставляет пул непроверенным и возвращает код **2**. `--skip-install`
предполагает, что зависимости и бинарный файл уже установлены.

Автоматического продолжения после сбоя нет. Для ручного восстановления сначала
сохраните конфигурацию и `deployment.json`, изучите ошибку, журнал соответствующей
службы и отчёт проверки. Удалять либо заменять следует только ресурсы этой попытки.
Нехватка RAM останавливает установку; меньшее количество не засчитывается как успех.

## Использование в парсерах

Идентификатор нового логического прокси — **`host:port:username`**. Дедупликация,
квоты и распределённые блокировки только по `host:port` объединят весь пул в один
прокси. Пароль не входит в идентификатор. Пул TCP/TLS-соединений должен учитывать
прокси-авторизацию; при смене логина используется отдельное соединение.

Проверены `aiohttp`, HTTPS-запросы `curl_cffi` и WSS через Node `ws` с
`https-proxy-agent`. Для Titan подготовлен параметр `TITAN_SHARED_PROXY_ENDPOINTS`:

```text
TITAN_SHARED_PROXY_ENDPOINTS=192.0.2.10:10000
```

В него включают только новые общие входные точки. Остальные пулы сохраняют прежние
Redis-ключи. Перед добавлением нового пула всем его потребителям нужна версия Titan
с поддержкой этого параметра и одинаковый список входных точек. Обновление скрипта
установки само по себе не переводит рабочие парсеры на новый пул.

## Работа службы и диагностика

```bash
systemctl status 3proxy-capacity.service
journalctl -u 3proxy-capacity.service
```

Служба включена на загрузку. `ExecStartPre` добавляет только отсутствующие адреса
из сохранённого проекта и проверяет DAD; далее запускается тот же конфиг с теми же
паролями и привязками. Ошибка создания пула останавливает и выключает только
созданные службы; конфигурации сохраняются для ручного разбора.
Если создание завершилось, но внешняя проверка не прошла, статус будет
`verification_failed`: служба остаётся запущенной для диагностики, установка
возвращает ошибку, автоматический повтор запрещён.

В `/var/log/3proxy/<project>.log` записываются время UTC, IP клиента, входящий порт,
исходящий IPv6, удалённый IP, код ошибки, длительность и байты. Логинов, паролей и
URL в журнале нет. Старые установленные форматы журналов сохраняются.
`3proxy-logrotate.timer` проверяет журналы каждую минуту: порог 16 МиБ, четыре сжатых
архива. HTTP-статус внутри HTTPS-туннеля прокси не видит.

Низкоуровневые инструменты `1_generate_proxy_configs.py`, `2_bind_ipv6_addresses.py`
и созданные ранее shell-скрипты сохранены для обслуживания старых установок.
Автоматический SSH-установщик использует новый режим создания общего порта и
не выполняет миграцию существующих пулов.

Проверить уже скачанный пул с другого компьютера:

```bash
venv/bin/python 4_proxy_checker.py --project-name capacity \
  --base-dir downloaded_configs/192.0.2.10
```

## Воспроизводимые испытания

`architecture_lab.py` и `architecture_workload.py` образуют отдельный стенд для
сравнения портовой схемы 3proxy, общего порта 3proxy и GOST. Контрольный HTTP/WSS
сервер не вызывает внешние API. Процессы генератора и тестовой цели должны иметь
`LimitNOFILE=65536`; для цели используются порты 18080/18443 вне диапазона
эфемерных клиентских портов. Стенд ограничен выделенным тестовым хостом.

Тесты логики установки:

```bash
venv/bin/python -m unittest discover
```

## Нагрузочные испытания через реальные API


`proxy_load_test.py` запускается отдельно от рабочих парсеров. Нужны окружение
`jup_async_parser`, соседний checkout `arb_parsers_models` и Node-зависимости его
Titan-транспорта. Для изолированной установки Node-зависимостей:

```bash
npm install --prefix capacity_results/node --no-package-lock --ignore-scripts \
  ws@8.21.3 https-proxy-agent@7.0.6
```

Пример HTTP-прогона (путь к интерпретатору замените на окружение парсера):

```bash
/path/to/jup_async_parser/.venv/bin/python proxy_load_test.py \
  --host 192.0.2.10 --interface net0 --parser-root /path/to/jup_async_parser \
  --proxy-file downloaded_configs/192.0.2.10/extracted_proxy \
  --profile http --rps 10 --ramp --output capacity_results/http.jsonl
```

Для WebSocket: `--profile ws --connections 100 --ramp`. Для совместного прогона:
`--profile mixed --connections 500 --rps 10 --ramp --ramp-axis http` либо
`--ramp-axis ws`. По умолчанию используются 60 секунд прогрева и 300 секунд
измерения на ступень. Ступени возрастают в 1,5 раза; HTTP сохраняет ограничение
профиля Llama/Base в один запрос в секунду на прокси. Для уточнения границы
запускайте отдельные ступени без `--ramp`. Для финальной проверки — `--duration 1800`.
В отдельных проверках передавайте `--baseline-p95-ms` с p95 успешной начальной
ступени, чтобы сохранить тот же порог допустимой HTTP-задержки.
Для интервала между обновлениями WS аналогичный параметр — `--baseline-ws-p95-ms`.
`--limit-proxies` ограничивает активный пул генератора, не количество развёрнутых
портов; поле `proxy_count` в результате отражает именно активный пул.

HTTP выполняет buy-котировку 200 USDT → ETH на Base через Llama/Kyber;
WebSocket подписывается на buy-котировки 50 USDT → SOL через Titan.
Ключ Llama читается из `.env` парсера. Данные и секреты парсеров не записываются
в отчёт, рабочие процессы и Redis не используются. Повторение одной пары
характеризует транспорт этого запроса, а не нагрузку всех возможных торговых пар.

На исследуемом сервере через Git должна быть установлена `capacity_monitor.py`.
Монитор передаёт показатели по одному SSH-соединению каждые пять секунд.
Результаты и ресурсные измерения сохраняются как JSONL. При 401/403/429,
ограничении подписок, нехватке ресурсов или ухудшении качества прогон прекращается.
Предел API и предел генератора не следует считать пределом прокси-сервера.
Счётчики охватывают весь измеряемый интервал; перцентили вычисляются по последним
200 000 валидным событиям каждого типа. Проверки качества выполняются каждые
пять секунд в течение всего измерения. Растущая очередь необработанных WS-сообщений
отдельно обозначается как ограничение генератора.

После единичного обрыва уже работающего WS с кодом 1006 тестер допускает одно
переподключение через тот же прокси с той же идентичностью клиента. Разрыв
учитывается как ошибка; более 1% разрывов от целевого числа WS за 60 секунд
останавливают этап. Повторный обрыв того же соединения, ошибка начального
подключения и ограничения API прекращают тест без дальнейших повторов.
В отчёт входят число переподключений, минимальное число открытых WS и максимальный
интервал между полезными обновлениями, включая восстановление соединения.
