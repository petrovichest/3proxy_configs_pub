# Архитектура и проверка IPv6-прокси

## Выбор реализации

Для автоматической установки выбран 3proxy 0.9.5 с одним процессом и одним
входящим портом. Статическое правило для каждого логина закрепляет исходящий IPv6.
Увеличение числа выданных адресов добавляет записи конфигурации, без отдельного
потока и слушающего сокета на каждый адрес.

```mermaid
flowchart LR
    A[HTTP / HTTPS / WSS клиент] --> B[Один IPv4-порт: авторизация]
    B --> C[Логин → фиксированный IPv6]
    C --> D[Исходящий сокет с этим IPv6]
    D --> E[Целевой сервис]
```

Соответствие загружается из локального конфига при старте. `parent extip` задаёт
исходящий адрес сокета. Установка включает IPv6 DNS-кэш 3proxy. IPv4-назначения и
IPv4-mapped адреса отклоняются, разрешение имён выполняется в режиме IPv6.

У 3proxy остаётся поток на активное соединение. Поэтому один слушатель уменьшает
расходы на неиспользуемые адреса, а бюджет активных соединений остаётся конечным.

## Что сравнивалось

- 3proxy: отдельный порт на IPv6, один либо несколько процессов.
- 3proxy: общий порт, логин выбирает IPv6.
- GOST 3.3.0: отдельный порт на IPv6 и исходящий адрес в `interface`.

Критерии выбора: корректная авторизация и все выходные адреса; не менее 99% заданного
HTTP RPS, отсутствие неожиданных разрывов WS, минимум 512 МиБ доступной памяти.
Существенным улучшением считалась экономия памяти либо рост устойчивой
производительности от 20%, при ухудшении p95 не более 10%.

Среди прошедших вариантов предпочтение отдаётся меньшей пиковой памяти группы
процессов. При разнице менее 10% учитываются CPU и объём необходимых изменений
клиентов. Размер прежней пачки 1 000 не принимается за оптимальный по умолчанию.

## Условия измерения

Сервер прокси: 1 vCPU, 1 962 МиБ RAM, без swap. Для сравнения использованы одинаковые
назначенные IPv6, бинарный файл 3proxy и контрольная цель. На интерфейсе во время
сравнения оставались все 9 000 исходных адресов, включая опыты с меньшими пулами.

Контрольная цель и генератор работают отдельно от прокси, с ограничением ресурсов.
HTTP: HTTPS-ответ с 4 096 байтами полезной нагрузки и задержкой цели 50 мс.
WSS: 4 096 байт полезной нагрузки на сообщение, 1,25 сообщения/с на соединение.
JSON и протокольные заголовки добавляют небольшой объём. Сжатие сообщений отключено.

В типовом сравнении: 60 секунд прогрева, затем 120 секунд измерения; HTTP подаётся
равномерно, сохраняет соединения и обходит активный пул. Для полного пула 9 000
используется более длительный прогрев. Активные подмножества в расширенной серии
распределены по всему списку. Перцентили учитывают все события измеряемого интервала.

Каждый вариант предварительно проходит проверку всех адресов, неверного пароля,
HTTP, HTTPS CONNECT, IPv4 и IPv4-mapped назначений. Проверка возвращённого IPv6
продолжается на каждом ответе и сообщении WSS во время нагрузки.

Память — максимальное наблюдённое `memory.current` всей группы процессов, включая
учтённую ядром память; доступная память — `MemAvailable` хоста. CPU относится ко
всему тестовому серверу. Монитор снимает показатели каждые две секунды. Защитная
остановка на 256 МиБ нужна для сохранности стенда; проходной запас выше — 512 МиБ.

Во всех этих точках получено около 103,9 успешного HTTP-запроса/с, без ошибок и
неожиданных разрывов WSS. Небольшая разница с 104 обусловлена незавершёнными запросами
на границе измерительного интервала. Экономия при 9 000 адресах — около 74%; при
2 000 одновременно используемых HTTP-адресах — около 26%.

В раннем сравнительном замере общего порта с 9 000 адресами использовался
`nscache`; окончательная установка использует `nscache6`. Контрольная цель задана
IPv6-адресом, поэтому DNS-разрешение в этом сравнении не выполняется.

Профиль со всеми 9 000 удерживаемыми HTTP-соединениями и 400 WSS не прошёл на
2 ГБ RAM в обеих схемах. Общий порт дошёл примерно до 9 231 активного соединения
до защитной остановки; отдельные порты — примерно до 5 562. Запас RAM оказался
ниже проходных 512 МиБ. Это остановки в прогреве, а не успешные измерения ёмкости.
9 000 выданных IPv6 и 9 000 одновременно удерживаемых TCP-соединений требуют
разного бюджета ресурсов.

GOST с 3 000 слушателями прошёл функциональную проверку, но при холодном старте
контрольной нагрузки достиг 100% CPU и 1 411 МиБ памяти группы. Запас памяти упал
до 197 МиБ, монитор остановил процесс. Полноценного измерения устойчивого RPS в
этом опыте нет. В этой версии выбор исходящего IP включает перебор интерфейсов и
их адресов при каждом новом соединении; на интерфейсе стенда было 9 000 IPv6.
После провала обязательной нагрузки этот вариант исключён из дальнейшего выбора.

## Проверка окончательной установки

24 сентября 2026 года новый установщик создал с нуля пул из 9 000 логинов на
подготовленном тестовом Ubuntu-сервере. IPv4, интерфейс и `/48` определены
автоматически. Все 9 000 прокси проверены снаружи; затем сервер перезагружен.
Служба и все адреса восстановились автоматически, хеши конфигов и паролей
сохранились. Повторное создание пула отклонено до изменения конфигурации.

После перезагрузки повторены проверка всех адресов и проверки клиентов. Проведён
часовой тест окончательной установки: **104 HTTP/с, 880 WSS и 1 000 удерживаемых
HTTP-соединений**, с 60 секундами прогрева. Активные идентичности распределены
по всему пулу из 9 000 адресов. На 30-й минуте все WSS планово переподключены,
с ограничением до 30 одновременных рукопожатий. Эта же совместная нагрузка до
установки прошла отдельный трёхминутный тест с переподключением.

| Показатель за час | Результат |
|---|---:|
| Успешный HTTP RPS | 103,997 |
| Успешных HTTP-запросов | 374 388 |
| HTTP p50 / p95 / p99 | 119 / 120 / 122 мс |
| Сообщений WSS | 3 956 236 |
| Ошибки HTTP / неожиданные разрывы WSS / неверный IPv6 | 0 / 0 / 0 |
| Восстановлено WSS при плановом переподключении | 880 из 880 |
| Максимальная пауза WSS, включая переподключение | 7 971 мс |
| Пиковая память группы службы, включая прогрев | 277,0 МиБ |
| Минимум доступной RAM | 1 264,0 МиБ |
| CPU сервера, среднее / максимум | 16,48% / 52,94% |
| Перезапуски службы / OOM / ListenDrops | 0 / 0 / 0 |

После нагрузки служба осталась активной и включённой; PID, конфиги, пароли и все
9 000 привязок сохранились. Исходная установка сохранена в отдельном архиве.
До нагрузки группа службы занимала 22,3 МиБ, после — около 58,2 МиБ.

Это квалификация транспорта с описанными выше размером сообщений, частотой и
политикой соединений. Предел производительности не установлен. Реальные API
этим часовым прогоном не проверялись. Предыдущие результаты с реальными API и
другим HTTP-пулом нельзя использовать для вычисления прямого коэффициента
ускорения новой архитектуры.

## Совместимость и границы применения

На общем порту с 9 000 логическими прокси проверены 20 распределённых по списку
идентичностей: 120 HTTPS-запросов через `curl_cffi 0.16.3` и 20 WSS-соединений через
Node 24.18.0, `ws` и `https-proxy-agent`. Ошибок или подмены исходящего IPv6 не было.
Последовательные и параллельные HTTPS-запросы использовали общий клиентский пул.

Дедупликация и блокировки должны учитывать `host:port:username`. В Titan это
включается отдельно для перечисленных `TITAN_SHARED_PROXY_ENDPOINTS`; для остальных
пулов Redis-ключи сохраняются. Повторное использование TCP-соединения относится к
одной прокси-идентичности.

Ресурсный бюджет суммируется по всем парсерам и клиентским сессиям. Несколько
соединений через один логин расходуют несколько слотов. Независимые сессии либо
разные целевые домены могут открывать дополнительные соединения к тем же прокси.
Слот обозначает соединение клиента с прокси; парный исходящий сокет уже учтён
в измеренном расходе ресурсов. Входящие и исходящие сокеты нельзя повторно
складывать при распределении этого бюджета между клиентами.
В Llama размер используемого списка ограничивается `LLAMA_ROBINHOOD_PROXY_LIMIT`;
значение 1 000 соответствует измеренному пулу для одной сессии с одним целевым
доменом. Сам параметр не ограничивает число соединений всех клиентов. При
нескольких независимых клиентах их суммарный бюджет должен укладываться в профиль.

Контрольный тест изолирует транспорт. Реальные ограничения API, размер сообщений,
частота обновлений, компрессия, TLS-переподключения и сетевые задержки требуют
проверки соответствующего сервиса. Значения из разных профилей нельзя складывать
или интерполировать как универсальную формулу ёмкости.

## Последующая проверка настоящих API

В реальных Robinhood/Titan-запросах обнаружен дополнительный расход CPU в
системном DNS-резолвере при 9000 назначенных IPv6. Исправление добавляет `nserver`
из системной DNS-конфигурации, чтобы задействовать резолвер и кэш 3proxy.
Контрольные цели выше использовали буквальный IPv6 и не проверяли этот путь.
Реальные результаты, покрытие пар и ограничения HTTP приведены в
[отдельном отчёте](real-workload.md). Синтетические 104 HTTP/с + 880 WSS не являются
квалификацией этой же нагрузки на API парсеров.
