# Миграция существующих IPv6-прокси

После завершённой миграции количество адресов увеличивается отдельным
[режимом расширения](expansion.md), с сохранением существующих доступов.
При наличии `expansion.json` текущие количество и хеши находятся в нём и
`pool.json`; исходный `deployment.json` хранит историю миграции.

## Контракт для потребителей

Один сервер принимает HTTP proxy/CONNECT на одном IPv4-порту. Пара
`host:port:username` идентифицирует логический прокси; логин выбирает закреплённый
выходной IPv6. IPv4 в клиентском списке — входной адрес сервера. Выход через IPv4
запрещён. Смена пароля не создаёт новую идентичность; смена логина требует отдельного
TCP/CONNECT-соединения. Нельзя объединять пользователей по одному `host:port`.

Список: `192.0.2.10:20000@shared_10000:<password>`.
URL клиента: `http://shared_10000:<password>@192.0.2.10:20000`.
Пароли при построении URL следует кодировать; генератор использует URL-safe символы.
Списки и миграционный журнал содержат секреты: 0600, каталоги 0700, без вывода в логи.

Прокси работают с IPv6-доступными целевыми сервисами. Количество IPv6 не задаёт RPS
или число допустимых WS. Ресурсы общие на сервере; технические `maxconn`, TasksMax и
LimitNOFILE не являются SLA. IPv6 из разных /64 одного /48 не дают независимую
репутацию /48 или ASN. Подтверждённые профили и их ограничения описаны в
[реальных испытаниях](real-workload.md) и [архитектуре](architecture.md).

## Подготовка рядом со старой службой

Код доставляется через commit → push → clone/pull. Режим `create` по-прежнему
отказывается работать поверх существующего пула. Для миграции нужен отдельный
каталог, по умолчанию `/home/3proxy_shared`; старый остаётся в
`/home/3proxy_configs_pub`.

```bash
.venv/bin/python remote_setup_script.py --mode migrate --phase prepare \
  --host proxy-host --listen-port 20000
```

Установщик проверяет старые конфигурации, службы, назначенные IPv6 и свободный порт.
Он сохраняет все старые IPv6 и число записей, создаёт один проект `shared` с отдельными
паролями, явными DNS-серверами и лимитом памяти с резервом 512 МиБ. Старая установка
продолжает обслуживать клиентов. Каждый новый логин проверяется снаружи с ожидаемым
IPv6. `--skip-check` возвращает 2 и запрещает преобразование списков до проверки.

Повторный `prepare` использует реквизиты из приватного `deployment.json`. Изменение
исходных конфигураций/бинарника или уже созданных файлов останавливает миграцию.
Частичный запуск можно повторить; старые службы при ошибке не останавливаются.

## Перенос потребителей

Журнал скачивается в `downloaded_configs/<host>/deployment.json` и содержит старые
и новые реквизиты. Не коммитить его в этот публичный репозиторий.

```bash
# Проверка без изменения файлов и без печати реквизитов
.venv/bin/python migrate_proxy_lists.py \
  --deployment downloaded_configs/proxy-host/deployment.json \
  --file /path/to/private-consumer/proxy/pool.txt
# Добавить --apply для записи. Для обратного преобразования использовать --reverse.
```

Выбирать все действующие списки, включая списки остановленных приложений.
Преобразователь сохраняет порядок, посторонние хосты и комментарии; неизвестный
прокси мигрируемого хоста блокирует все выбранные файлы до записи. Уже заменённая
запись не изменяется повторно. Реквизиты доставлять в потребители через Git только
после проверки приватности репозитория.

В Titan установить `TITAN_SHARED_PROXY_ENDPOINTS` для новых входных адресов.
Ключи блокировок нового и старого подключения различаются при одинаковом выходном
IPv6: обе группы BUY/SELL нужно остановить, дождаться завершения дочерних процессов
и старых соединений, затем запустить с новым списком. TTL proxy lock — 60 секунд,
token claim — 120 секунд после последнего обновления. Чужие блокировки не удалять.

Сначала восстановить Titan и проверить свежесть BUY/SELL, затем перезапускать
зависимые event sell-боты. Их стартовая проверка требует свежие CEX + Titan
котировки. Отдельно проверить холодный старт SELL: HTTP-источник начальной цены
может не покрывать токены, для которых уже работают BUY-подписки. Клиентская
инструкция описывает допустимый источник цены для расчёта размера подписки;
нельзя подменять отсутствующую SELL-котировку ценой BUY.

Проверять HTTP, WS и запросы по событиям. Списки могут кэшироваться в памяти;
обновление файла не гарантирует переключение уже работающего клиента. Перезапускать
только работающих потребителей изменённых файлов, учитывая активные операции.
Сохранять размеры пулов, частоту запросов и список остановленных приложений.

## Завершение и откат

После проверки клиентов и наблюдения рабочей нагрузки:

```bash
.venv/bin/python remote_setup_script.py --mode migrate --phase finalize --host proxy-host
```

`finalize` требует полной внешней проверки, исправной новой службы, резерва памяти
и отсутствия соединений к старым портам. Только затем старые службы отключаются;
выходные IPv6 не удаляются. Конфигурации старой установки сохраняются.

```bash
.venv/bin/python remote_setup_script.py --mode migrate --phase rollback --host proxy-host
```

Сначала восстанавливаются старые службы. Если к общей службе ещё подключены клиенты,
сохраняется `rollback_pending` (код 2). Вернуть списки текущего этапа через Git,
перезапустить затронутых потребителей и повторить `rollback`: общая служба будет
отключена после ухода клиентов. Состояние и реквизиты сохраняются для диагностики.

Перед завершением сверить серверные и проектные инструкции с реально установленными
портами и ревизиями. Архивные списки не являются источником для новых запусков.
