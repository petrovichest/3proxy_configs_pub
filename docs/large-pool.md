# Испытание крупного общего пула

Количество логинов не равно числу соединений или квоте API. Внутри одной `/64`
все адреса разделяют риск блокировки этой подсети. Проверка транспорта на нашей
контрольной цели не подтверждает допустимую нагрузку внешнего API.

## Установка рядом с приложениями

Для нового пула используйте `provision_server.py create` либо удалённый установщик
с явными `--memory-max-mib`, `--reserve-memory-mib`, `--cpu-quota-percent`.
Пример бюджета: 8192 МиБ, резерв хоста 32768 МиБ, CPU 400% (четыре логических CPU).
Без параметров сохраняется прежний режим: доступная память минус 512 МиБ,
без ограничения CPU. `maxconn=16000` и ограничения числа потоков сохраняются.

Ресурсы записываются в приватный журнал первой установки. Резерв проверяется при
запуске, подтверждении и расширении; расширение также проверяет оценку размера
конфигурации против сохранённого бюджета службы. Это не прогноз памяти соединений.
Fresh-install guard сохраняется. Рост выполняется только через `expand_server.py`.

Для испытания используйте этапы `prepare`, `apply`, затем внешнюю проверку всего
пула и контрольную нагрузку; только после успеха — `verify`. До подтверждения
доступен явный откат расширения. Подтверждённый пул автоматически не откатывается.
Новые IPv6 не удаляются при откате: адреса могут использоваться другими службами.

## Контрольная цель

Код на всех хостах доставляется через Git. В отдельном приватном `--lab-dir`
запустите `architecture_workload.py fixture` с параметрами `--fixture-ipv4`,
`--fixture-ipv6` и повторяемым `--allow-source CIDR`. Разрешайте только адреса
генератора и проверяемую подсеть. Дополнительно требуется секретный токен.
Смена адресов или списка допуска требует нового каталога стенда.

Стенд создаёт `fixture.json`, `fixture.crt` и `fixture.key`. На клиент передаются
только JSON с токеном и публичный сертификат; закрытый ключ остаётся на цели.
Файлы сохраняются приватно, реквизиты не публикуются. Проверка TLS включена.
Порты цели — 18080 и 18443. Цель должна быть на другом хосте: локальный маршрут
не проверяет выход IPv6 в сеть провайдера.

Клиентские команды `check` и `load` принимают тот же `--lab-dir` и `--pool`.
Формат приватного JSON-пула: массив записей с `host`, `port`, `username`, `password`,
`ipv6`. `check --check-concurrency 20 --report REPORT.json` проверяет все записи,
ошибочный пароль, запрет IPv4 и IPv4-mapped, разделение пользователей при reuse.
Отчёт не содержит паролей; в нём количество, хеш входного пула и задержка полного
HTTPS-запроса без reuse по десяти частям списка. Это не изолированное время авторизации.

## Порядок измерений

Перед установкой собрать 10 минут исходных показателей хоста и работающих приложений.
Ступени каталога: 10000, 25000, 50000, 100000. После проверки каждой ступени повторить
100 HTTP/с, HTTP-пул 1000 и 400 WSS: 60 секунд прогрева и 300 секунд измерения.
Нагрузка распределяется по всему каталогу; запросы не обращаются к API парсеров.

На последней успешной ступени проверить отдельно HTTP 100/250/500/1000 запросов/с,
WSS 1000/2500/5000/10000 и соответствующие совместные пары. Сообщения WSS — 4 КиБ
полезной нагрузки, 1.25 сообщения/с; HTTP-цель добавляет задержку 50 мс.
Последний прошедший совместный профиль выдержать час, переподключить WSS на 1800-й
секунде. Цель и генератор имеют свои ограничения CPU/RAM и наблюдаются отдельно.

Прекратить тест при неправильном IPv6, OOM, неожиданном рестарте, RAM хоста ниже
32 ГиБ, CPU выше 75% минуту, трафике выше 700 Мбит/с либо минутном ухудшении
HTTP p95 рабочих приложений более 20% или доли просроченных котировок более 1 п.п.
При потере наблюдения прекратить нагрузку. Защита останавливает только созданные
этим испытанием процессы; приложения PM2 и старые прокси не перезапускаются.

Проходной профиль: минимум 99% заданного RPS, правильные IPv6, отсутствие ошибок
HTTP и неожиданных разрывов WSS. Ограничение генератора/цели не объявляется пределом
прокси. Каталог остаётся отдельно от рабочих списков парсеров.
